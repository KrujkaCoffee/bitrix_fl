# Пилот заявки на подбор

Услуга **344025** получает структурированную форму по присланному Excel. После отправки создаются задача внутренних сервисов и связанная вакансия **1118**, категория **23**, стадия `DT1118_23:NEW`. Отклики **1114**, категория **22**, продолжают использовать существующую связь с вакансией.

## Границы первого изменения

Пилот по умолчанию выключен. После отдельного включения новая форма доступна только пользователям **1466** и **3076** из `recruitment/config.php`. Остальные пользователи работают с прежней формой услуги. Общий `TaskServiceBuilder` и репозиторий-справочник `bitrix` не изменяются.

Обязательны название вакансии и явно выбранный заказчик. Остальные реквизиты Excel пока необязательны. Инициатор определяется по авторизованному пользователю, дата заявки — по серверному времени, подразделение — по существующему справочнику инфоблока55. Оплата с оговорками, наставник и желаемый срок выхода сохраняются текстом. «Количество кандидатов» — исходное число из заявки, не число откликов и пока не утверждённый план найма. Текстовая «Подпись» не запускает согласование.

Дата открытия подбора, дата фактического выхода, стадии и права CRM этим изменением не меняются. Заказчик записывается в существующее поле `UF_CRM_19_1794913385`. Добавления в наблюдатели и выдачи CRM-доступа нет. Назначенный конструктором услуги HR выступает ответственным и контекстом штатной операции добавления CRM; проверки прав не отключаются.

У кадровой задачи устанавливается `GROUP_ID=0`, чтобы не наследовать общую группу20 из конструктора. Аудиторы и соисполнители остаются из настроек кадровой услуги — перед пилотом проверьте их состав. Вложения загружаются в личный Диск автора с проверкой права добавления и прикрепляются штатным механизмом задач, без публичных ссылок и копирования в CRM.

## Установка

1. После слияния PR обновите рабочую копию `KrujkaCoffee/bitrix_fl` обычным `git pull` из каталога компонента `/home/bitrix/www/local/components/kuratovru/services.main/`. В обновление должен попасть весь каталог `recruitment/`. Корневой `config.php` и закупочный регламент не меняются. Отдельное приложение и регистрация модуля не требуются. Репозиторий `KrujkaCoffee/bitrix` — полная копия коробки в `/home/bitrix`; для этого изменения его обновление не требуется.
2. На сервере проверьте PHP-файлы. В корне компонента:

   ```bash
   find recruitment tools tests -name '*.php' -print0 | xargs -0 -n1 php -l
   php -l class.php
   ```

3. Из административной PHP-консоли запустите **PLAN**:

   ```php
   $hrRecruitmentMode = 'PLAN';
   require '/home/bitrix/www/local/components/kuratovru/services.main/tools/recruitment_admin.php';
   ```

   Вывод должен содержать `STATUS=COMPLETE`, категорию23, список новых полей и необходимость создания журнала. PLAN не меняет данные. Существующие поля с другим типом блокируют установку. Скрипт не меняет типы, не удаляет поля и не создаёт демонстрационных вакансий.

4. В той же консоли выполните отдельный запуск с `$hrRecruitmentMode = 'APPLY';`. Он создаёт отсутствующие поля вакансии и закрытый служебный журнал `b_kelast_hr_request`. Повторный APPLY переиспользует их. Пилот остаётся выключенным. Изменения DDL не объединяются в транзакцию; при частичной ошибке исправьте причину и повторите PLAN/APPLY.
5. Следующим отдельным запуском задайте `$hrRecruitmentMode = 'ENABLE';`. Он проверяет полную схему и native права назначенного HR, затем включает пилот. При ошибке включения новая форма не активируется. Проверьте фактическое чтение CRM под HR и под посторонним сотрудником: право добавлять не доказывает изоляцию чтения.
6. Откройте заново страницу внутренних сервисов под участником пилота. При необходимости очистите кеш компонента/обновите страницу с полной перезагрузкой скрипта.

Служебный скрипт работает только внутри уже загруженного Б24 от администратора. Запуск по прямому URL и самостоятельный CLI-запуск не выполняют установку.

## Приёмочный прогон на портале

Используйте явно тестовую должность и несекретные данные.

| Проверка | Ожидаемый результат |
|---|---|
| Пустой заказчик/название, некорректное количество | Ошибка до загрузки файлов и создания задачи |
| Заказчик отличается от автора | Обе роли сохранены раздельно |
| Оплата «от … до вычета», срок «до …» | Текст сохранён без потери условий |
| Одна отправка | Одна задача и одна вакансия с номером исходной задачи |
| Ответственный и начальная стадия | HR из услуги, категория23, `DT1118_23:NEW`, `OPENED=N` |
| Двойное нажатие/повтор после сетевой ошибки | Тот же ключ и существующий результат, новая задача не создаётся |
| Повтор с изменёнными данными и прежним ключом | Конфликт; запись не перезаписывается |
| Вложение | Личный Диск автора, файл открывается у участников задачи, отсутствует общая группа20 |
| Возврат браузером после отправки | Повтор заблокирован, новая отдельная заявка начинается явной кнопкой |
| Другой пользователь/другая услуга | Прежний интерфейс и прежний маршрут |
| HR и посторонний сотрудник | Фактические права чтения соответствуют настроенным ролям CRM |
| Завершение исходной задачи | Вакансия автоматически не закрывается |

Новые поля доступны в CRM. При необходимости HR добавляет нужные поля в расположение карточки штатным редактором, это не меняет модель данных. Автоматического изменения общей раскладки карточек нет.

## Повторы и восстановление

Ключ запроса хранится в `sessionStorage` без содержимого формы. На сервере ключ связан с автором и услугой, проверяется хеш исходных данных. Именованная блокировка БД охватывает загрузку файлов и создание задачи. Журнал сохраняет проверенные реквизиты отдельно от изменяемого описания задачи.

После подтверждения task ID повтор создаёт только недостающую вакансию. Поиск вакансии по `UF_CRM_HR_SOURCE_TASK` и её создание выполняются под отдельной блокировкой задачи с чтением master-БД. Если CRM успела записать элемент, но подтверждение потерялось, повтор находит его. Два совпадения требуют разбора, новое не создаётся.

Если конструктор выбросил исключение после получения task ID, уже созданная задача сохраняется. Если процесс оборвался до подтверждения ID, состояние становится неопределённым: повторный `build()` запрещён. Это сознательно требует сверки администратором, поскольку общий конструктор не записывает ключ запроса атомарно вместе с задачей. Автоматической гарантии восстановления task ID при любом аварийном завершении нет.

В браузере перед запросом сохраняется состояние `SENDING`. После потери ответа или перезагрузки кнопка «Проверить отправку» получает результат по прежнему ключу и автору, без повторной передачи заполненной формы. Если сервер ещё не начинал создание задачи, можно продолжить заполнение; если задача уже есть — открывается существующая задача. «Новая заявка» очищает также выбранные вложения.

Режим `STATUS` выводит последние30 состояний, автора и ID без текста заявок. Для заявки с подтверждённой задачей и статусом `VACANCY_PENDING`:

```php
$hrRecruitmentMode = 'RETRY';
$hrRecruitmentRequestKey = '64-символьный REQUEST_KEY из STATUS';
require '/home/bitrix/www/local/components/kuratovru/services.main/tools/recruitment_admin.php';
```

Для `TASK_CREATING`/`TASK_UNCERTAIN` администратор сначала находит существующую задачу и проверяет, что это именно нужная заявка. Затем `RECONCILE` с тем же `REQUEST_KEY` и `$hrRecruitmentTaskId = 123;` привязывает её. Проверяются услуга, автор, ответственный, подразделение и точное исходное описание. Следующий `RETRY` завершает только запись CRM. Если задачу не нашли, не сбрасывайте журнал наугад: результат надо установить до новой отправки. Ключ из браузерного сообщения переводится в ключ журнала по формуле `hash('sha256', $actorId . ':344025:' . strtolower($browserKey))`. После сверки пользователь повторно нажимает «Проверить отправку» и получает подтверждённый результат.

## Отключение

Запуск служебного скрипта с `$hrRecruitmentMode = 'DISABLE';` возвращает прежнюю форму услуги. Уже открытая кадровая форма с ключом запроса не провалится в прежний обработчик. Данные CRM и журнала сохраняются. При откате кода сначала отключите пилот, затем верните компонент целиком. Поля, вакансии, задачи и журнал автоматически не удаляются.
